# Как я работал с ИИ-агентами

## Принципы

1. Решения принимаю я, агент предлагает варианты. Архитектуру и необратимые действия
   согласовываю до правок.
2. Одна задача — один проверяемый результат. Большие изменения разбиваю на этапы
   с тестами после каждого.
3. «Готово» значит: код собирается, тесты зелёные, сценарий проверен.
4. Секреты не попадают в контекст. `.env` не вывожу и не копирую в документы; для
   live-проверок значения загружаются в окружение, но ключи не печатаются. Для БД
   использую временные контейнеры.
5. Без явной команды не коммичу и не пушу.

## Рабочий цикл

```
Задача
  → уточняющие вопросы и ограничения
  → план (что меняем, как проверим)
  → маленькая правка
  → gofmt / go vet / go test
  → при необходимости: PostgreSQL, race, live Groq
  → отчёт: что сделано, что проверено, что осталось
  → следующая итерация
```

Если агент нашёл проблему, он показывает её отдельно: что не так, насколько это
критично и какой минимальный фикс предлагает.

## Как я ставлю задачи

Размыто:

> «Сделай AI для бота».

Нормально:

> «Проверь текущий LLM-путь, найди краевые случаи, код пока не меняй. Отдельно:
> что сломается при неоднозначном удалении?»

> «Исправь только подтверждение удаления. Покажи план и тесты. Не коммить.»

> «Прогони unit и интеграционные тесты. Если нужна БД — подними временный контейнер
> и не трогай мой `.env`.»

## Что это дало

Сначала список проблем, потом фиксы — так меньше соблазна переписать всё сразу.
После каждого блока есть зелёный набор тестов, а не большое «готово», в котором
непонятно, что сломалось. Кроме unit-тестов проверял PostgreSQL, реальный Groq и
запуск Telegram polling; диалог в Telegram потом прошёл вручную.

## Как это проявилось в проекте

- Базовый AI-flow: strict JSON Schema и типизированный `Intent`, выполнение только в Go.
- Отдельно проверены и исправлены: неоднозначное удаление, поиск цели по датам и
  категориям, устаревшая сумма при update, неполные итоги списков, таймзона, таймауты.
- Сравнение моделей: GPT-OSS-120B и Qwen на русских командах. Выбор зафиксирован в env.
- Найден реальный дефект: reasoning-токены съедали `max_tokens`, strict JSON обрезался.
  Исправил увеличением лимита и `reasoning_effort: low`.
- Сделал набор из 36 фраз для eval; live-проверки отделены от обычных тестов.
  Полный набор 36/36 пройден на GPT-OSS-120B с паузами из-за free tier.

## Журнал изменений

После заметных этапов (API, схема БД, сквозной flow, Compose) добавляю короткую
запись в `docs/IMPLEMENTATION_LOG.md`: что изменилось, как проверено, что осталось.
Это не git-история и не дублирование кода.

## Инструменты и границы

- Coding-ассистент помогает с кодом, тестами, разбором ошибок и документацией.
- LLM в приложении — отдельная сущность; у неё нет доступа к репозиторию, БД и
  секретам.
- Тесты без сети — обычный `go test`. Сеть и реальный провайдер — только по флагам
  `LLM_INTEGRATION=1` / `LLM_EVAL=1`.
- Для проверки БД — временный PostgreSQL-контейнер и `TEST_DATABASE_URL`.

## Что можно улучшить дальше

- Хранить pending-состояния в БД и переживать рестарт.
- Добавить inline-кнопки подтверждения.
- Поддержать несколько трат в одном сообщении.
- Сохранять отчёт полного eval в CI или в README при изменениях промпта.
