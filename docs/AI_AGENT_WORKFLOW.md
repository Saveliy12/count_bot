# Как я работал с ИИ-агентами

## Принципы

1. **Агент предлагает — я решаю.** Архитектурные и необратимые действия требуют
   подтверждения.
2. **Маленькие итерации.** Одна задача → один проверяемый результат. Большие изменения
   разбиваются на этапы с тестами после каждого.
3. **Проверка важнее уверенности.** «Готово» означает: код собран, тесты прошли,
   поведение проверено. Не «модель так сказала».
4. **Секреты не попадают в контекст.** `.env` не выводится и не копируется в документы.
   Для разрешённых live-проверок значения загружаются в окружение процесса, но ключи
   не печатаются и не попадают в отчёты; для БД используются временные контейнеры.
5. **Никаких коммитов без разрешения.** Git-операции — только по явной команде.

## Рабочий цикл

```
Задача
  → уточняющие вопросы и ограничения
  → план (что меняем, как проверим)
  → маленькая правка
  → gofmt / go vet / go test
  → при необходимости: PostgreSQL, race, live Groq
  → отчёт: что сделано, что проверено, что осталось
  → следующая итерация
```

Если агент нашёл проблему, он не прпускает/скрывает её, а показывает: что именно не так,
насколько это критично и какой минимальный фикс предлагает.

## Как я ставлю задачи

Плохо:

> «Сделай AI для бота».

Хорошо:

> «Проверь текущий LLM-путь, найди corner cases, код пока не меняй. Отдельно:
> что сломается при неоднозначном удалении?»

> «Исправь только подтверждение удаления. Покажи план и тесты. Не коммить.»

> «Прогони unit и интеграционные тесты. Если нужна БД — подними временный контейнер
> и не трогай мой `.env`.»

## Что даёт такой процесс

- **Аудит отдельно от правок.** Сначала список проблем, потом фиксы — меньше соблазна
  «улучшить всё сразу».
- **Проверяемые этапы.** После каждого блока есть зелёный набор тестов, а не большой
  «готово», в котором непонятно, что сломалось.
- **Живые проверки.** Кроме unit-тестов: PostgreSQL, реальный Groq и проверка запуска
  Telegram polling
- **Честные ограничения.** В документации прямо написано, что не проверено и что
  осталось.

## Как это проявилось в проекте

- Базовый AI-flow: strict JSON Schema + типизированный `Intent`, выполнение только в Go.
- Отдельно проверены и исправлены: неоднозначное удаление, поиск цели по датам и
  категориям, устаревшая сумма при update, неполные итоги списков, таймзона, таймауты.
- Сравнение моделей: GPT-OSS-120B и Qwen на русских командах. Выбор зафиксирован в env.
- Найден реальный дефект: reasoning-токены съедали `max_tokens`, strict JSON обрезался.
  Исправлено увеличением лимита и `reasoning_effort: low`.
- Создан opt-in eval-набор из 36 фраз; live-проверки отделены от обычных тестов.
  Полный набор 36/36 пройден на GPT-OSS-120B с паузами из-за free-tier.

## Журнал изменений

После значимых этапов (API, схема БД, межслойный flow, Compose) добавляется короткая
запись в `docs/IMPLEMENTATION_LOG.md`: задача, изменённые слои, новый сценарий,
проверки и ограничения. Это не git-история и не дублирование кода — только то, что
поможет восстановить ход мыслей и собрать финальный `ARCHITECTURE.md`.

## Инструменты и границы

- Coding-ассистент помогает с кодом, тестами, разбором ошибок и документацией.
- Runtime-LLM в приложении — отдельная сущность; она не имеет доступа к репозиторию,
  БД и секретам.
- Тесты без сети — обычный `go test`. Сеть и реальный провайдер — только по флагам
  `LLM_INTEGRATION=1` / `LLM_EVAL=1`.
- Для проверки БД — временный PostgreSQL-контейнер и `TEST_DATABASE_URL`.

## Что можно улучшить дальше

- Хранить pending-состояния в БД и переживать рестарт.
- Добавить inline-кнопки подтверждения.
- Поддержать несколько трат в одном сообщении.
- Сохранять отчёт полного eval в CI или в README при изменениях промпта.
- Оформить README с диаграммой и коротким demo-сценарием.
