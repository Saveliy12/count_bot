# Журнал значимых изменений

Короткие записи по этапам: что менял, как проверял, что осталось.

## Backend: схема, сервис и API

Собрал основу: миграции `families`, `users`, `expenses` и 14 категорий, модели с
`decimal`, сервис с проверкой владельца и семьи, репозитории и REST API панели.
Миграции применяются при старте, есть health/ready, request ID, логи и graceful
shutdown.

Проверил unit- и интеграционные тесты на временной схеме PostgreSQL, `go vet`,
`go build` и `-race`. UI и Compose на этом этапе ещё не было.

## Docker: образ и Compose

Собрал multi-stage `Dockerfile` (Go 1.26 → Alpine) и `.dockerignore`. В runtime
попадают только бинарник и CA-сертификаты, запуск от uid 10001, миграции встроены
через `go:embed`. Образ получился около 21.6 MB, `.env` внутри нет.

Дальше добавил `compose.yaml`: PostgreSQL с healthcheck и volume, приложение стартует
после `service_healthy`. Для контейнера отдельный `COMPOSE_DATABASE_URL`, для
локального `go run` остаётся `DATABASE_URL`. Наружу только loopback-порты.

Проверил на изолированном project name: миграции, CRUD через API, graceful stop,
данные переживают `docker compose down` и повторный запуск.

## Telegram-бот и LLM-парсер

Бот принимает текст и превращает его в `llm.Intent` через Groq со strict JSON
Schema. Дальше всё делает Go: проверяет сумму, дату, категорию и владельца, ищет
цель для update/delete и вызывает `ExpenseService`. У модели нет доступа к БД.

Удаление только после «да/нет» и с проверкой снимка записи, чтобы не удалить
изменённую трату. Сумма ищется по точному совпадению, чтобы `350` не цепляло `1350`.
Для `update` есть `old_amount`. Списки считаются SQL-агрегатом.

По устойчивости: общий timeout, повтор при 429/5xx, `reasoning_effort: low` и
`max_tokens=600`, иначе strict JSON обрезался на reasoning-токенах.

Проверил unit/DB-тесты, `-race` и живой сценарий create → list → update → delete.
Eval тогда был на 33 фразах, позже расширил до 36.

## Панельный API: категории, итоги, демо-участник

Добавил `GET /api/v1/categories`, чтобы не дублировать русские названия 14 категорий
во фронтенде. Итоги по семье считает `SummaryByFamily` с теми же фильтрами, что и
список; в ответе появились `total` и `count`.

Чтобы панель работала сразу после первого `docker compose up`, добавил
`SEED_DEMO_USER`: на пустой семье создаётся «Демо-пользователь», если пользователи
уже есть — ничего не происходит.

Проверил unit- и интеграционные тесты, `-race` и отдельный Compose на чистой базе.

## Панель: статика, список и фильтры

Панель отдаёт тот же Go-сервер: `internal/api/web` с `go:embed`, маршруты `/` и
`/static/`, неизвестные `/api/...` остаются JSON-404. Отдельного frontend-контейнера
нет.

Дальше собрал список: участники, категории, фильтры по участнику, периоду и
категории, пагинация «Показать ещё», пустое и ошибочное состояние, карточки на
мобильном. По умолчанию открывается текущий месяц, итог берётся из API, а не
считается по загруженной странице.

Проверил в headless Chrome: фильтры, пустое состояние, свой диапазон дат,
пагинацию 50 → 56, отсутствие горизонтального скролла на 390px. Плюс `node --check`,
`go test`, `go vet`, `go build`.

## Панель: создание, редактирование, удаление

Добавил `<dialog>` для создания и редактирования, `POST` и `PATCH`, удаление через
нативный `confirm` и `DELETE`. Сумма принимается с запятой или точкой, серверные
ошибки раскладываются по полям, после успеха список и итог перезагружаются, строка
подсвечивается.

В edit участник заблокирован: API не меняет владельца. Комментарий можно очистить.

Проверил в headless Chrome создание, редактирование, отмену и подтверждение удаления,
обновление `total/count`, мобильный диалог. Плюс `node --check`, `go test`, `go vet`,
`go build`.

## Полировка панели

Прошёлся по панели перед E2E и поправил мелочи: «Повторить» после ошибки сохраняет
фильтры, в edit-диалоге заголовок «Изменение записи», корректный текст для неполного
диапазона дат, русские сообщения для сетевых и 400/404/409/5xx, удаление уже
исчезнувшей траты перезагружает список.

Проверил те же сценарии в headless Chrome и мобильные карточки с двумя действиями.

## Повтор запроса при сбое strict-JSON

Иногда модель под strict-схемой возвращала невалидный JSON. Добавил повтор при HTTP
400 с `json_validate_failed` или `failed_generation` в пределах общего числа попыток.
Постоянная ошибка запроса по-прежнему возвращается пользователю.

Проверил unit-тестом; на тот момент полный eval был 36/36.

## Неоднозначные цели и выбор по номеру

Если под «удали такси» подходит несколько трат, бот показывает до пяти вариантов с
ID, датой, суммой и комментарием. Можно ответить номером (`6`) или уточнить дату
(`удали такси 20.10.2026`). Выбор сохраняется в pending и ведёт к подтверждению
удаления или к patch. Добавил нормализацию `DD.MM.YYYY`, одиночная дата больше не
печатается как диапазон. `/start` и неизвестные команды сбрасывают pending.

Проверил unit-тесты выбора цели, даты и сброса, `-race` и три целевых eval-кейса.

## Ответы бота в HTML и полный eval

Перевёл ответы на Telegram HTML: эмодзи по действию, `<b>` для заголовков, `<code>`
для сумм, дат и ID. Пользовательские данные экранируются. Заодно добавил защиту от
голого числа без pending и сброс pending на `/start` и неизвестных командах.

Проверил unit-тесты, `-race`, живой сценарий с Groq и PostgreSQL, полный eval 36/36
на GPT-OSS-120B. Из-за free tier запускал с `LLM_EVAL_DELAY=18s`. Реальный диалог в
Telegram потом проверил вручную.
