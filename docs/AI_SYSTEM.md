# AI в проекте: техническое описание

Документ описывает **runtime-LLM** внутри приложения. Про то, как проект пишется с
помощью coding-ассистентов, — в `AI_AGENT_WORKFLOW.md`.

## 1. Роль LLM

LLM — только парсер естественного языка в типизированное намерение. Она:

- получает текст сообщения и текущую дату;
- возвращает JSON строго по схеме (`llm.Intent`);
- **не имеет доступа к БД**, не вызывает инструменты и не выполняет действия.

Решение, валидацию, поиск владельца, подтверждение удаления и запись выполняет Go.

```
Telegram
  → bot.Runner (long polling, один worker)
  → bot.Handler (только личные чаты, EnsureUser)
  → bot.LLMProcessor (pending-состояния, выбор действия)
  → llm.Client (Groq, strict JSON Schema)
  → llm.Intent
  → Go: валидация, owner-scoped поиск, подтверждение
  → service.ExpenseService
  → repository → PostgreSQL
```

## 2. Модель и провайдер

| Параметр | Значение |
|---|---|
| Провайдер | Groq, OpenAI-совместимый endpoint |
| Модель по умолчанию | `openai/gpt-oss-120b` |
| Альтернатива | `qwen/qwen3.8-27b` через `LLM_MODEL` |
| Формат | `response_format: json_schema`, `strict: true` |
| Температура | `0` |
| `max_tokens` | `600` |
| Reasoning | `reasoning_effort: "low"` для моделей `openai/gpt-oss*` |

Почему GPT-OSS: на замерах он стабильно прошёл целевые сценарии, Qwen показал
сопоставимое качество, но дал сбой strict-JSON и более долгий холодный старт.
Модель вынесена в env, поэтому переключение не требует правок кода.

## 3. Схема намерения

Основные поля `llm.Intent`:

| Поле | Смысл |
|---|---|
| `action` | `create`, `list`, `update`, `delete`, `clarify` |
| `amount` | новая сумма, строкой в JSON |
| `old_amount` | старая сумма для проверки перед update |
| `category` | новая категория |
| `date_hint` | новая дата: `today`, `yesterday`, `YYYY-MM-DD` |
| `comment`, `clear_comment` | новый/очищаемый комментарий |
| `target_mode` | `latest`, `id`, `query` |
| `target_id`, `target_query` | точный ID или текстовый поиск старой траты |
| `target_date_hint`, `target_category` | дата/категория **старой** траты для поиска |
| `period_preset`, `period_from/to` | период для `list` |
| `clarification` | вопрос пользователю для `clarify` |

`date_hint` и `target_date_hint` — разные вещи: первое задаёт новую дату, второе
ищет старую запись. То же для `category` / `target_category`.

## 4. Действия

- **create** — обязательны сумма и категория; дата по умолчанию сегодня; затем
  `CreateExpense` с проверкой владельца.
- **list** — период (по умолчанию текущий месяц), опциональная категория.
  Итог и количество считаются SQL-агрегатом `SUM/COUNT`, показываются последние 10.
- **update** — цель ищется по `latest` или `query` с учётом `target_date_hint` и
  `target_category`. При явном `id` запись выбирается по ID с проверкой владельца.
  `old_amount` проверяет, что выбрана та самая трата. Пустой патч отклоняется.
- **delete** — цель ищется так же, но удаление **только после подтверждения**
  «да/нет» в течение 2 минут.
- **clarify** — сохраняет контекст вопроса на 5 минут; следующий ответ
  передаётся модели вместе с исходным сообщением и вопросом.

Поиск по `query` идёт по комментарию, категории и **точному** совпадению суммы
(запрос `350` не матчит `1350`). Просматривается до 5 страниц по 200 записей;
если совпадений может быть больше, действие не выполняется.

## 5. Безопасность

- Все запросы к тратам owner-scoped; чужая запись возвращает `not found`.
- Удаление атомарное: `DELETE ... WHERE id, user_id, amount, category, spent_at,
  comment, updated_at` совпадают со снимком. Если запись изменили через API —
  удаление не произойдёт, пользователь получит просьбу повторить.
- Текст пользователя в промпте помечен как данные. Prompt injection не может изменить
  формат ответа и обойти проверки прав/данных, но может повлиять на выбранное действие;
  поэтому удаление подтверждается, а цель проверяется по дате, категории и сумме.
- В Groq уходит только текущее сообщение (и контекст уточнения), без строк из БД.
  Ключ провайдера используется в заголовке авторизации и не попадает в текст запроса.
- Логи не содержат тел ответов LLM, ключей и токенов; для ошибок пишутся статус
  и request ID.
- REST API панели без авторизации — требование локального демо; веб-интерфейс ещё
  в работе. Это не production-решение.

## 6. Конфигурация

| Переменная | Назначение |
|---|---|
| `GROQ_API_KEY` | ключ провайдера; без него бот работает на заглушке |
| `LLM_MODEL` | модель, по умолчанию `openai/gpt-oss-120b` |
| `LLM_BASE_URL` | по умолчанию `https://api.groq.com/openai/v1` |
| `LLM_TIMEOUT` | общий дедлайн запроса, по умолчанию `20s` |
| `TIMEZONE` | бизнес-зона для «сегодня», по умолчанию `Europe/Moscow` |
| `DATABASE_URL`, `HTTP_ADDR`, `TELEGRAM_BOT_TOKEN` | БД, HTTP и Telegram |

Retry: до 3 попыток при 429/5xx, учитывается `Retry-After`, но ожидание
ограничено 4 секундами; общий timeout действует на все попытки.

## 7. Тесты и фактический статус

- Unit-тесты: fake-провайдер, без сети.
- Интеграционные: временная схема PostgreSQL через `TEST_DATABASE_URL`.
- Live-тесты с Groq — только по явному флагу:
  - `LLM_INTEGRATION=1` — сквозной сценарий;
  - `LLM_EVAL=1` — оценка качества по набору из 33 русских фраз.
- Проверено: `go test ./...`, `go test -race`, `go vet`, `go build`,
  интеграция с PostgreSQL.
- Живой сценарий `LLMProcessor → Groq → PostgreSQL` (create → list → update → delete)
  прошёл; отдельный реальный Telegram-update в этом прогоне не отправлялся.
- Целевая выборка eval (даты/категории/update/delete): **10/10**.
- Ранее на create-выборке: **8/8**.
- Полный набор 33/33 одним прогоном пока не зафиксирован — это нужно сделать
  отдельно, чтобы не выдавать частичный результат за полный.

## 8. Ограничения

- Нет постоянного хранения pending-состояний: рестарт сбрасывает подтверждение
  и контекст уточнения.
- Несколько трат в одном сообщении не поддерживаются.
- Нет inline-кнопок подтверждения — используется текст «да/нет».
- Нет дедупликации повторно доставленных Telegram update: после сбоя возможна
  повторная обработка сообщения.
- Docker Compose реализован и проверен; веб-панель и README ещё не реализованы.
