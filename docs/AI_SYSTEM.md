# AI в проекте: техническое описание

Документ про LLM в приложении. Как проект писался с coding-агентом, в
`AI_AGENT_WORKFLOW.md`.

## 1. Роль LLM

LLM разбирает текст в типизированное намерение. Она получает сообщение и текущую дату,
возвращает JSON по схеме `llm.Intent` и не имеет доступа к БД: не вызывает инструменты
и ничего не пишет.

Валидацию, поиск владельца, подтверждение удаления и запись выполняет Go. Схема потока
в [README](../README.md#архитектура).

## 2. Модель и провайдер

| Параметр | Значение |
|---|---|
| Провайдер | Groq, OpenAI-совместимый endpoint |
| Модель по умолчанию | `openai/gpt-oss-120b` |
| Альтернатива | `qwen/qwen3.8-27b` |
| Формат | `response_format: json_schema`, `strict: true` |
| Температура | `0` |
| `max_tokens` | `600` |
| Reasoning | `reasoning_effort: "low"` для моделей `openai/gpt-oss*` |

Мне нужны были три вещи: строгий JSON, ответ за пару секунд и бесплатный тариф.
GPT-OSS-120B на Groq закрыл все три.

| Модель | Проверка | Результат |
|---|---|---|
| `openai/gpt-oss-120b` | 8 фраз, живой Groq | 8/8, медиана 0.93 с, максимум 1.18 с |
| `qwen/qwen3.8-27b` | 5 фраз | 5/5, медиана 0.62 с; в раннем прогоне был сбой strict JSON |
| `openai/gpt-oss-20b` | короткая проба | `json_validate_failed` |

Полный набор прогнан только на GPT-OSS-120B. Qwen на короткой выборке был даже
быстрее, но полного набора на ней нет, а в раннем прогоне она сорвалась на strict JSON.
Поэтому основная модель GPT-OSS-120B.

Модель задаётся через `LLM_MODEL`, код менять не нужно.

## 3. Схема намерения

Основные поля `llm.Intent`:

| Поле | Смысл |
|---|---|
| `action` | `create`, `list`, `update`, `delete`, `clarify` |
| `amount` | новая сумма, строкой в JSON |
| `old_amount` | старая сумма для проверки перед update |
| `category` | новая категория |
| `date_hint` | новая дата: `today`, `yesterday`, `YYYY-MM-DD` |
| `comment`, `clear_comment` | новый/очищаемый комментарий |
| `target_mode` | `latest`, `id`, `query` |
| `target_id`, `target_query` | точный ID или текстовый поиск старой траты |
| `target_date_hint`, `target_category` | дата/категория **старой** траты для поиска |
| `period_preset`, `period_from/to` | период для `list` |
| `clarification` | вопрос пользователю для `clarify` |

`date_hint` и `target_date_hint` — разные вещи: первое задаёт новую дату, второе
ищет старую запись. То же для `category` / `target_category`.

## 4. Действия

- `create` — обязательны сумма и категория; дата по умолчанию сегодня; затем
  `CreateExpense` с проверкой владельца.
- `list` — период (по умолчанию текущий месяц), опциональная категория.
  Итог и количество считаются SQL-агрегатом `SUM/COUNT`, показываются последние 10.
- `update` — цель ищется по `latest` или `query` с учётом `target_date_hint` и
  `target_category`. При явном `id` запись выбирается по ID с проверкой владельца.
  `old_amount` проверяет, что выбрана та самая трата. Пустой патч отклоняется.
- `delete` — цель ищется так же, но удаление только после подтверждения «да/нет»
  в течение 2 минут.
- `clarify` — сохраняет контекст вопроса на 5 минут; следующий ответ передаётся
  модели вместе с исходным сообщением и вопросом.

Поиск по `query` идёт по комментарию, категории и точной сумме: `350` не совпадает с
`1350`. Просматриваются до 5 страниц по 200 записей, фильтрация по тексту и сумме идёт
в Go после выборки. На большой истории цель может не найтись, это осознанное
ограничение вместо полнотекстового поиска в SQL.

Если совпадений несколько, бот показывает до 5 вариантов с ID; можно ответить номером
(`6`) или уточнить дату (`удали такси 20.10.2026`). Если совпадений слишком много,
действие не выполняется без уточнения.

## 5. Безопасность

- Все запросы к тратам проверяют владельца в сервисе; чужая запись возвращает `not found`.
- Удаление атомарное: `DELETE ... WHERE id, user_id, amount, category, spent_at,
  comment, updated_at` совпадают со снимком. Если запись изменили через API,
  удаление не произойдёт, пользователь получит просьбу повторить.
- Текст пользователя в промпте помечен как данные. Prompt injection не может изменить
  формат ответа и обойти проверки прав или данных, но может повлиять на выбранное
  действие. Поэтому удаление подтверждается, а цель проверяется по дате, категории и
  сумме.
- В Groq уходит только текущее сообщение (и контекст уточнения), без строк из БД.
  Ключ провайдера используется в заголовке авторизации и не попадает в текст запроса.
- Логи не содержат тел ответов LLM, ключей и токенов; для ошибок пишутся статус
  и request ID.
- Панель и REST API работают без авторизации: так требует локальное демо. Для
  продакшена нужна авторизация.

## 6. Конфигурация LLM

| Переменная | Назначение |
|---|---|
| `GROQ_API_KEY` | ключ провайдера; без него бот работает на заглушке |
| `LLM_MODEL` | модель, по умолчанию `openai/gpt-oss-120b` |
| `LLM_BASE_URL` | по умолчанию `https://api.groq.com/openai/v1` |
| `LLM_TIMEOUT` | общий дедлайн запроса, по умолчанию `20s` |
| `TIMEZONE` | бизнес-зона для «сегодня», по умолчанию `Europe/Moscow` |

Остальные переменные в [README](../README.md#конфигурация).

Повтор: до 3 попыток при 429/5xx, учитывается `Retry-After`, но ожидание ограничено
4 секундами; общий timeout действует на все попытки.

## 7. Тесты и статус

- Unit-тесты: fake-провайдер, без сети.
- Интеграционные: временная схема PostgreSQL через `TEST_DATABASE_URL`.
- Живые тесты с Groq только по флагу: `LLM_INTEGRATION=1` для сквозного сценария,
  `LLM_EVAL=1` для оценки качества.
- Полный набор 36/36 пройден на GPT-OSS-120B. Из-за бесплатного тарифа запуск идёт с
  `LLM_EVAL_DELAY=18s`; один временный сбой strict JSON за прогон повторяет клиент.
- Набор писал я и подстраивал под него промпт, поэтому он ловит регрессии, но не
  доказывает качество на произвольных фразах.
